** TODO Fuzz, cruft
Fuzz is a term multiplied by a small constant.
These show up because when solving for \(p\)'s and \(b\)'s, sometimes a number that should be zero comes out instead with a small magnitude.
Cruft is where there's a wrong function, for example, an \(x^2\) that should be a \(2(1 - \cos x)\) or conversely.
Defuzzing is where I go through the expression tree and convert tiny constants to 0.
I'm kind of stuck with the cruft.
Correctness ends up being subjective:
What if you can leave out a fairly large fuzz term, but the remaining coefficients are pretty far off?
Then it's hard to document:
You have to record a judgment call for every sample.
Also, a long evolution time gives Jessamine time to eliminate cruft.
** TODO Inventory intuition
If the inventory is too big, the search wastes time considering functions that can't possibly be correct, and risks incorporating cruft.
If the inventory is too small, it will have to find an approximation (series, rational function) because the necessary function isn't available.
** TODO No single perfect configuration
Some kind of adaptive search, VNS, or sweeping configuration is necessary to solve everything.
** TODO Numerical thresholds
Not easy to set because the solving process for a correct expression might vary in how low it can get the MSE.
** TODO Subsetting
Random subsets of a data set are used for evolving individual populations.
The whole data set is used to compute the MSE in the analysis.

*** Polynomials
are no problem.
*** Rational functions
can be a problem.
Mainly the challenge with the ~d_bacres~ data sets is that they are from trajectories that don't pass close to \(x = 0\), so there's minimal evidence that a series in \(1/x\) is incorrect.
I did find a way to cheat to make a couple of perfect solutions show up.
*** Trig functions
are mostly no problem.
This works largely thanks to two important features:
- initialization using only indices for \(x_j\)s and \(p_j\)s as operands
- weighting of mutations so that we don't get so many nested trig functions
The ~shearflow~ data sets are hard using the SRB operation inventory because it has to discover \(\cos(y) \cos(x) / \sin(y)\), which requires a multiplication layer and a division layer.
If you "cheat" and include \(\cot\) in the operation inventory, success happens much more often, since \(\cot(y) \cos(x)\) requires only one multiplication layer.
Additional complications are that sometimes Jessamine finds these almost-right expressions:
- a translation identity, \(\sin(x + p)\) instead of \(\cos(x)\), and then it solves for \(p \approx \pi/2\)
- a Pythagorean identity
